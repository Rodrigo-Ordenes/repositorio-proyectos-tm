# Plan P2: modularizar el cliente y el servidor y evaluar las subidas sin base64

**Estado:** propuesta. No se implementa nada antes del 19 de noviembre de 2026. Recomiendo además esperar al cierre de los proyectos (11 de diciembre), para no tocar la estructura del sitio mientras el curso lo usa.

**Restricciones que se mantienen:** sin dependencias en tiempo de ejecución (Python estándar y JavaScript sin frameworks), CSP `default-src 'self'`, rutas y contratos de la API sin cambios, datos personales fuera de git. La red de seguridad es la suite (`bash pruebas/ejecutar.sh`, 374 verificaciones con los PR #3 a #6 integrados) más un recorrido en el navegador al final de cada paso.

## Situación medida (7 de noviembre de 2026)

| Pieza | Medida |
|---|---|
| `static/app.js` | 1.144 líneas; 90 superan los 400 caracteres; la más larga tiene 2.281 |
| `server.py` | 2.924 líneas; unas 100 funciones; enrutamiento en dos cadenas de `if path == …` (`route_get`, `route_post`, unas 66 rutas) |
| Subida máxima (8 MB de evidencia + 8 MB de STL) | Cuerpo JSON de 21,3 MB (+33 % por base64). Memoria del proceso: 29 MB en reposo y **120 MB de pico** (+91 MB, unas 5,7 veces el tamaño de los archivos) |

El pico se explica porque el servidor lee todo el cuerpo (`rfile.read(length)`), lo convierte a JSON y decodifica el base64: en memoria conviven la cadena del cuerpo, el objeto JSON y los bytes decodificados de cada archivo. Con `ThreadingHTTPServer`, las subidas simultáneas suman. En el plan Starter de Render (512 MB), cuatro entregas grandes al mismo tiempo dejarían el proceso cerca del límite.

## 1. Cliente: formatear y luego modularizar

**Paso 1.1: solo formato (sin cambios de comportamiento).** Partir las líneas largas: plantillas HTML en varias líneas y una sentencia por línea en los manejadores. Hay dos opciones:
- **(a)** Ejecutar una vez un formateador (`npx prettier@3`) sin agregarlo al repositorio. Es rápido y uniforme, pero usa una herramienta externa por única vez.
- **(b)** Formatear a mano por secciones. Toma más tiempo y no deja rastro externo.

Recomiendo **(a)**: el resultado se revisa como cualquier diff y el proyecto no gana dependencias. Verificación: el diff no cambia tokens (comparar `node --check` y una minificación simple antes y después) y la suite pasa.

**Paso 1.2: módulos nativos del navegador.** Pasar a `<script type="module">`, que la CSP actual ya permite (`'self'`), sin empaquetador. Hoy no hay manejadores en línea (la CSP los prohíbe), así que no hay referencias globales desde el HTML que romper. Propuesta de división:

| Módulo | Contenido |
|---|---|
| `nucleo.js` | `api`, `esc`, `notify`, estado de sesión, enrutador, `go` |
| `ingreso.js` | Pantalla de ingreso, invitaciones y retorno después de entrar |
| `asignatura.js` | Portada de la asignatura, catálogo, filtros y pestañas |
| `entrega.js` | Formulario de entrega, borrador local, alternativas y aviso de Drive |
| `ficha.js` | Detalle del trabajo, foro, preguntas de control, coevaluación y visor STL |
| `panel/*.js` | Panel docente por sección: accesos y códigos, revisión, tiquetes, encuestas, auditoría, respaldos y cohortes |
| `informe.js`, `proyeccion.js` | Informe con gráficos y modo proyección |
| `paginas.js` | Ayuda, privacidad, consentimiento y kit |

Orden: primero las funciones puras (`parseStl`, `barChart`, normalización de listas y temporizador); después las páginas que dependen de ellas. Un PR por módulo.

**Paso 1.3: pruebas unitarias sin dependencias.** Con módulos, las funciones puras se pueden probar con `node --test`, que ya está en los runners de GitHub Actions: parser STL, formato del temporizador, clasificación de alternativas y gráficos. Se agrega `pruebas/js.sh` a la suite.

**Criterio de terminado:** suite en verde; recorrido en el navegador de las tareas a–e y de la proyección, a 375 px y en escritorio, en ambos temas; auditoría de contraste sin fallas.

## 2. Servidor: separar en módulos sin cambiar el proceso

Se mantiene un solo proceso con la biblioteca estándar, y `server.py` sigue siendo el punto de entrada (el `startCommand` de Render no cambia). Propuesta:

| Módulo | Contenido |
|---|---|
| `app/config.py` | Variables de entorno, `PROJECTS`, dominios y límites |
| `app/db.py` | Conexión, esquema, migraciones aditivas y respaldos |
| `app/acceso.py` | Sesiones, códigos personales, del curso y SOS, Google OIDC y límites de intentos |
| `app/archivos.py` | Validación de PDF, DOCX y STL y almacenamiento |
| `app/auditoria.py` | Eventos, huellas HMAC y retención |
| `app/rutas/*.py` | Manejadores por área (entregas, foro, tiquetes, encuestas, panel, informe) |
| `app/cli.py` | `codigo`, `codigo-sos`, `respaldo`, `diagnostico`… |

**Enrutamiento:** reemplazar las cadenas de `if path == …` por una tabla `(método, patrón) → manejador`. Se hace por grupos: primero se registran las rutas nuevas en la tabla y se deja la cadena antigua como respaldo; cuando un grupo pasa la suite, se borra su parte de la cadena.

**Reglas:** cada PR solo mueve código (sin cambiar lógica) o solo cambia lógica, nunca ambas cosas. `python3 -m py_compile` y la suite en cada paso. Evitar importaciones circulares: `config` y `db` no importan nada del proyecto.

**Criterio de terminado:** suite en verde; `python3 server.py diagnostico` igual que antes; despliegue de prueba en Render sin cambios de configuración.

## 3. Subidas sin base64: evaluación

| Opción | Cómo | Memoria | Complejidad | Riesgos |
|---|---|---|---|---|
| **A. Mantener base64 en JSON** | Como hoy | ~5,7 veces el tamaño de los archivos por solicitud (medido) | Ninguna | Picos con subidas simultáneas; +33 % de transferencia en conexiones móviles |
| **B. `multipart/form-data`** | El formulario envía `FormData`; el servidor interpreta multipart | Baja si se procesa por partes hacia disco | Media-alta: `cgi` está obsoleto y desaparece en Python 3.13, así que habría que interpretarlo a mano o con `email.parser`, que lee todo en memoria | Un parser propio es superficie de errores |
| **C. Subida directa por archivo (recomendada)** | `PUT /api/uploads?kind=evidencia\|modelo` con el archivo como cuerpo crudo, leído en bloques de 1 MB hacia un archivo temporal; responde un `upload_id`. La entrega JSON referencia ese id | Constante (~1 MB por subida) | Media: un endpoint, una tabla de subidas temporales y limpieza de huérfanas (> 24 h) | Dos solicitudes por entrega; hay que validar que el id pertenece a quien entrega |

**Recomendación: C.** Usa solo la biblioteca estándar, valida el contenido igual que hoy (cabeceras de PDF, DOCX y STL) sobre el archivo temporal, evita el +33 % en redes móviles y deja la memoria acotada sin un parser multipart propio. Además permite mostrar el progreso de la subida en el cliente.

**Pruebas previstas para C:**
- subida de 8 MB con memoria pico < 40 MB (misma medición de hoy);
- rechazo de más de 8 MB sin leer el resto del cuerpo;
- un `upload_id` ajeno es rechazado;
- un id vencido es rechazado;
- las huérfanas se limpian;
- las entregas con base64 siguen aceptándose durante una transición (un semestre) y luego se retiran.

## Orden propuesto y fechas

1. Después del 11 de diciembre: paso 1.1 (formato), en un PR.
2. Diciembre–enero: pasos 1.2 y 1.3 (módulos y pruebas JS), un PR por módulo.
3. Enero: módulos del servidor y tabla de rutas, un PR por grupo.
4. Antes del semestre 2027-1: opción C de subidas, con transición de base64.
